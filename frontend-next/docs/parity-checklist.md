## 미검증 항목과 사유

로그인 후 경기 선택 → 대기열 → 좌석 선점 → 주문 생성 → 결제 준비까지는 실제
백엔드로 확인했다(2026-08-08, 경기 117 `[대기열 체험]`, 주문
`ORD-20260808-8F12E5`). 아래는 남은 항목이다.

1. **PG 결제 승인과 실패**. Toss 결제창은 카드 정보 입력을 요구하므로 Claude가
   수행할 수 없다. 클라이언트 키는 `test_ck_`로 시작하는 샌드박스 키이므로 실제
   금액은 청구되지 않는다. 사용자가 직접 결제창을 열어 승인·실패 경로와 그 이후의
   완료 화면·티켓 발급을 확인해야 한다.
2. **대기 중 화면**. 데모 백엔드가 단일 사용자에게 즉시 입장을 내주어 순위·진행률
   표시가 화면에 머무르지 않았다. 다중 사용자 부하가 필요하다.
3. **선점 해제와 주문 취소**. 결제 검증용 예약·주문을 남겨두느라 실행하지 않았다.
4. **두 앱의 상태 변경 시나리오 동시 비교**. 같은 포트를 쓰므로 순차 실행만
   가능하고, 서로 겹치지 않는 테스트 사용자·경기·좌석 데이터가 필요하다.

## 고친 결함

### 좌석 첫 진입 시 전 구역 좌석이 한 그리드에 섞여 나오던 문제

`hooks/use-seats.ts`의 좌석 쿼리가 `gameId`만 있으면 실행되어, 구역을 고르기 전
첫 진입에서 `GET /games/{id}/seats`를 **구역 없이** 호출했다. 백엔드는 이때 전
구역 좌석을 돌려주므로 화면은 500석을 `seatRow`로만 묶어, A열에 101구역 1번과
102구역 1번이 나란히 놓이는 형태로 그렸다.

기존 Vite는 좌석 단계에 들어올 때 `zones.data[0].zoneId`로 **첫 구역을 자동
선택**하고 그 구역 좌석만 조회한다(`frontend/src/App.tsx:618-630`). 같은 동작이
되도록 `useSeats`가 구역이 정해진 뒤에만 조회하고, 사용자가 아직 고르지 않았으면
첫 구역을 파생값으로 채우도록 고쳤다. 스토어에 값을 밀어 넣지 않아 "자동으로
채운 구역"과 "사용자가 고른 구역"이 섞이지 않는다.

검증: 실서버 경기 121 첫 진입에서 좌석 **50석**, 그리드 내 구역 `["101"]`,
안내 문구 `101의 실제 좌석을 선택하세요.`를 확인했다. 회귀 테스트
`test/hooks/use-seats.test.tsx`를 추가했고, 수정을 되돌리면 좌석 요청이
`''`(구역 없음)로 나가 실제로 실패하는 것을 확인했다.

### 선점 해제 후 다시 선점하면 조용히 실패하던 문제

입장 토큰은 1회용이다. `useReservation`의 예약 생성은 성공 직후
`storage.local.remove("queueToken")`으로 토큰을 소비하고, `api/client.ts`는
저장소에 토큰이 있을 때만 `Queue-Token` 헤더를 붙인다. 따라서 선점을 해제한 뒤
다시 선점하면 헤더 없이 요청이 나가고 백엔드가 거부한다. **백엔드는 규칙대로
동작한 것이고 문제는 화면 쪽이었다.**

기존 Vite는 이 상황을 두 가지로 처리한다. 예약 성공 시 `queueToken: null`로
만들어 `selectionLocked`가 참이 되므로 **좌석 선택 자체가 잠기고**
(`frontend/src/App.tsx:1447`), 취소할 때
`"좌석 선점을 해제했습니다. 현재 입장 토큰은 사용되어 새 선점은 다시 예매해야 합니다."`
를 안내한다(`:702`).

Next는 `queueToken`만 지우고 예매 스토어의 `queueTokenExpiresAt`은 남겨 두어
좌석 선택이 계속 열려 있었고, 좌석 화면에 Alert 자체가 없어 실패 원인도 보이지
않았다. 그래서 버튼을 눌러도 아무 일이 없는 것처럼 보였다.

수정: 토큰을 소비할 때 `setQueueExpiry(null)`을 함께 호출해 잠금이 걸리게 하고,
좌석 화면에 예약 생성·취소 오류와 해제 안내를 기존 화면과 같은 위치에 표시한다.
회귀 테스트 2건을 `test/app/games/seats-page.test.tsx`에 추가했으며, Alert
렌더링을 지우면 두 테스트가 실제로 실패하는 것을 확인했다.

## 알려진 잔여 차이

1. Tailwind v4는 `max-[900px]:`를 `not (min-width: 900px)`로 컴파일해 **정확히
   900px를 제외**한다. Vite의 `@media (max-width: 900px)`는 900px를 포함한다.
   1px 경계 차이이며 기존 코드에서도 같은 방식을 쓰고 있어 새 breakpoint 체계를
   만들지 않았다.
2. 대기열 화면 버튼의 hover `translateY(-1px)` 미세 동작을 색상 변화만으로
   단순화했다.
3. `useAuth`를 상단 바와 페이지가 각각 호출하므로 `consumeAuthCallback()`이
   consumer 수만큼 실행된다. 첫 호출이 같은 동기 실행 안에서 `replaceState`로
   쿼리를 지우기 때문에 실제로는 안전하지만, 이 안전성은 우연에 가깝고 테스트가
   없다. 비동기 정리로 바뀌면 조용히 깨질 수 있다.
