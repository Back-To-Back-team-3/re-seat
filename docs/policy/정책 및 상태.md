## 2. 시간·TTL 정책

### 2.1 TTL 표

| 항목 | 값 | 의미 | 근거 |
| --- | --- | --- | --- |
| JWT Access | 1시간 | 인증 토큰 수명 | 예매 플로우 전체 커버 |
| JWT Refresh | 14일 | 재발급 토큰 수명 | 일반적 표준 |
| SSE 연결 유지 | 60초 | 서버가 연결을 끊는 정상 주기 | 프록시 타임아웃 회피 |
| SSE 재연결 유예 | 150초 | 순번을 유지해주는 이탈 판정 유예 | 모바일 네트워크 전환(재연결) 여유  |
| Queue-Token `expires_at` | 21분 | 동시 입장 슬롯 점유 시간 | 좌석 탐색 3분 + HOLD 상한 18분 |
| 좌석 탐색 `seat_browsing_expires_at` | 3분 | 선점 없이 탐색만 하는 시간 | — |
| 좌석 선점 HOLD | 10분 | 좌석이 특정인에게 묶이는 시간 | — |
| 결제 기한 `payment_deadline` | 8분 | 결제 진행 시간 | 주문 생성 시점부터 |
| HOLD 연장 상한 | 18분 | 최초 선점 시점 + (10분 + 8분) | 공식 = 최초 선점 시점 + (10분 + 8분) |
| 만료 스케줄러 주기 | 10초 | 상태 정리 주기 | 데모 규모 적정 |
| 티켓 환불 기한 | 경기 시작 24시간 전 | 환불 요청 마감 | 일반 티켓팅 관행 |
- SSE 연결 유지와 SSE 재연결 유예
    - 60초 종료는 장애가 아니라 정상 사이클이므로 클라이언트가 조용히 재연결한다.
    - 150초는 재연결이 지연되어 순번을 잃었다고 판정하는 기준이다.
- 좌석 반환 지연 목표 구분
    - 결제 실패·취소 경로: 실패 콜백에서 즉시 반환. 목표 p99 ≤ 1초
    - HOLD 만료 경로: 만료 스케줄러(10초 주기) 기반 반환. 목표 p99 ≤ 12초
    - 티켓 환불 경로: `REFUNDED` 확정 트랜잭션에서 반환. 목표 p99 ≤ 1초

### 2.2 불변식

```
payment_deadline    = 주문 생성 시각 + 8분
hold_expires_at     = min( max(기존 hold_expires_at, payment_deadline), 
											     최초 선점 시각 + 18분 )
Queue-Token TTL     = 좌석 탐색 3분 + HOLD 상한 18분 = 21분

불변식: hold_expires_at >= payment_deadline
```

- 연장 값은 `reservations.hold_expires_at`과 묶인 모든 `game_seats.hold_expires_at`에 동일 트랜잭션에서 반영한다. 한쪽만 갱신하면 Redis–DB 정합성 불일치(B4)가 재발한다.
- 만료 스케줄러는 `WHERE status='HELD' AND hold_expires_at <= now()` 조건부 원자적 UPDATE로 수행하고, 주문 생성은 예약 행을 비관적 락으로 잡은 뒤 연장한다. 두 경로가 같은 행을 경합하기 때문이다.

**재선점 시 HOLD 상한 보정 규칙**

- 선점 취소 후 동일 Queue-Token으로 재선점하면 최초 선점 시각이 바뀌지 않으므로 HOLD 상한(최초 선점 시각 + 18분)이 재선점 시각 기준보다 일찍 도래할 수 있다.
- 이 경우 다음 두 조건을 재진입 전에 검사한다.
    1. Queue-Token 잔여 TTL > 0 (만료된 토큰은 재선점 불가)
    2. `재선점 시각 + 결제 기한(8분) ≤ 최초 선점 시각 + 18분`
        - 이 조건을 만족하지 못하면 `HOLD_EXTENSION_LIMIT_EXCEEDED`(409)를 반환하고 대기열 재진입(Queue-Token 재발급)을 안내한다.
- 주문 생성 시에도 `주문 생성 시각 + 결제 기한(8분) ≤ 최초 선점 시각 + 18분` 을 다시 검사한다.
    - 이 조건을 만족하지 못하면 `HOLD_EXTENSION_LIMIT_EXCEEDED` (409)를 반환하고 대기열 재진입 (Queue-Token 재발급)을 안내한다.

| 구간 | 복구 기준 | 복구 방법 | 재진입 조건 |

    - 주문만 만료되고 예약이 `HOLDING`으로 남는 상태는 사용자가 재주문도 재선점도 불가능한 갇히는 경로이므로 허용하지 않는다.

## 3. Queue-Token 정책

### 3.1 정의

- Queue-Token: 이 사용자는 이 경기 대기열을 정상 통과했고, 아직 구매를 마치지 않았다는 자격 증명
- 수량 제한 수단으로 사용하지 않는다. 수량 제한은 서버 집계 검증이 단독으로 책임진다.
- 저장 구조:
    - `admission_tokens` 테이블(MySQL, JPA Entity).
    - 클라이언트에도 토큰 발급이 필요하므로 클라이언트에는 SSE `admit` 이벤트로 전달한다.
- 복구 기준 :
    - 최초 좌석 선점 전에는 Queue-Token이 `ACTIVE` 이고 `seat_browsing_expires_at(3분)` 이내
    - 최초 선점 완료 이후에는 Queue-Token이 `ACTIVE` 이고 `expires_at(21분)` 이내

### 3.2 소비 시점

| 구분 | 내용 |
| --- | --- |
| 소비 시점 | 티켓 발급 성공 시 `ACTIVE → USED` |
| 좌석 선점 시 | 검증만 수행하고 소비하지 않는다. |
| 취소 시점 | 대기 취소 또는 SSE 재연결 유예(150초) 만료 시 대기 이력은 `CANCELED`, `ACTIVE`  Queue-Token은 `REVOKED`로 전환한다. |
| TTL | 21분으로 통일한다. |
- 토큰이 최대 21분간 동시 입장 슬롯을 점유해 슬롯 회수가 늦어진다. 티켓 발급 완료 시점에 즉시 슬롯을 회수하고, 미사용 토큰은 만료 스케줄러가 `EXPIRED`로 정리해 완화한다.
- 선점을 취소해도 토큰은 `ACTIVE`로 남아 있으므로 재선점에 그대로 사용한다. `reactivateToken`은 구현하지 않는다.

### 3.3 최초 좌석 탐색

- Queue-Token 발급 후 최초 좌석 선점까지 3분의 탐색 제한을 적용한다.
- 3분 안에 최초 좌석 선점이 완료되면 완료시간을 `seat_browsing_completed_at` 에 최초 한 번만 기록한다.
- 최초 선점 이후 좌석을 취소하거나 재선점해도 기존 완료 시간을 유지하며 탐색제한을 다시 적용하지 않는다.
- 최초 선점 없이 탐색 시간이 만료되면 Queue-Token을 `BROWSING_EXPIRED` 로 전환한다.
- 탐색 만료된 사용자는 자동으로 대기열에 재진입시키지 않고 예매 버튼부터 다시 진행한다.

### 3.4 재발급 기준

- 티켓 발급으로 토큰을 소진한 뒤 추가 구매를 원하는 사용자
- 티켓 환불이 완료되어 `REFUNDED` 상태가 되고 잔여 수량이 회복된 사용자
- TTL이 만료되었거나 토큰이 `REVOKED`되어 새로 진입하는 사용자
- `BROWSING_EXPIRED`로 최초 탐색이 종료된 사용자

## 4. 운영·정합성 정책

| 항목 | 정책 |
| --- | --- |
| 대기열 | 경기 선택 시점에 순번 없는 1차 진입 게이트를 통과해야 대기열에 진입한다.<br>대기열은 경기별로 관리하며 입장 인원은 초당 1명부터 시작해 측정 결과에 따라 조정한다. |
| 대기열 진입 | `booking_status`가 `OPEN`인 경기에만 진입을 허용한다.<br>검증에 실패한 요청은 Kafka 이벤트를 발행하거나 대기열에 등록하지 않고 거절 사유를 반환한다. |
| 대기열 중복 진입 | 다른 경기에서 대기 중이거나 `ACTIVE` Queue-Token을 보유한 사용자의 신규 진입을 거절한다.<br>거절 사유는 사용자·경기별로 구분한다. |
| 대기열 거절 | 거절 결과를 SSE로 전달한 뒤 연결을 종료하고 서버의 연결 정보를 정리한다. |
| 입장 권한 | 좌석 조회·선점 전에 유효한 Queue-Token과 CAPTCHA 검증을 통과해야 한다. |
| 최초 좌석 선점 기한 | 대기열 통과 시점부터 3분 |
| 좌석 선점 | 선점 성공 시점부터 10분 |
| 좌석 반환 | 예약 취소·선점 만료 시, 그리고 티켓 환불이 완료(`REFUNDED`)된 시점에 좌석을 `AVAILABLE`로 되돌린다.<br>`REFUND_PENDING`·`REFUND_FAILED` 구간에서는 `SOLD`를 유지한다.<br>환불 확정 전에 좌석을 풀면 환불 실패 시 티켓은 살아 있는데 좌석은 재판매된 상태가 되어 복구가 불가능하다. |
| 좌석 차단 | `AVAILABLE` 좌석만 `BLOCKED`로 전이할 수 있다.<br>`HELD`·`SOLD` 좌석은 차단 대상에서 제외하고 사유를 응답에 명시한다. |
| 재고 오픈 | 동일 경기에 대한 좌석 재고 오픈은 원자적으로 1회만 성공한다(`SEAT_INVENTORY_ALREADY_OPENED`). |
| 예매 상태 전이 | 경기별 예매 오픈은 원자적으로 1회만 성공한다.<br>관리자 두 명이 동시에 오픈해도 중복 전이가 발생하지 않아야 한다. |
| 주문·결제 기한 | 주문 생성 시점부터 8분. |
| 타이머 관계 | 결제 기한까지 선점을 연장하되 최초 선점 시점부터 최대 18분을 넘지 않는다.  |
| 결제 | 주문별 멱등키로 중복 승인 차단한다. |
| 취소(티켓 환불 기한) | 경기 시작 24시간 전까지 가능하며, 관리자 강제 취소는 사유와 집행자를 기록한다.<br>예약 취소와 주문 취소는 이 기한이 아니라 HOLD TTL·결제 기한을 따른다. |
| 취소 API 멱등성 | 이미 취소된 예약에 대한 재취소 요청은 200으로 멱등 처리하고, 만료된 예약의 해제 요청은 `PRE_RESERVATION_EXPIRED`(410)를 반환한다. |
| 환불 식별자 | 취소 대상은 `ticketId`로 지정한다. 예매번호(`order_no`)는 취소 실행 키가 아니라 조회·CS 응대용이다.<br>환불 금액은 클라이언트 값을 신뢰하지 않고 `order_items.price`에서 서버가 역산한다. |
| 환불 이력 선기록 | 취소 이력은 `payment_cancels`에 `PENDING`으로 선기록한 뒤 PG 호출 결과에 따라 `DONE`/`FAILED`로 전이한다.<br>재시도는 새 행을 만들지 않고 기존 행을 `FAILED → PENDING`으로 되돌린다. |
| 환불 중복 요청 | 티켓 상태가 `REFUND_PENDING`·`REFUND_FAILED`·`REFUNDED`이면 PG를 호출하지 않고 DB 상태만으로 응답한다.<br>중복 환불의 1차 방어선은 PG가 아니라 내부 상태 검증이다. |
| PG 중복 취소 응답 | PG가 "이미 취소된 거래"로 응답하면 실패가 아니라 성공으로 간주하고<br>`payment_cancels.status → DONE`, `tickets.status → REFUNDED`로 진행한다.<br>해당 응답은 자금 이동이 이미 완료됐다는 확정 신호이므로 DB만 동기화하면 된다. |
| 환불 실패 처리 | PG 취소가 네트워크·서버 오류로 실패하면 `payment_cancels.status → FAILED`,<br>`tickets.status → REFUND_FAILED`로 두고 좌석·결제 금액은 변경하지 않는다.<br>사용자 재시도와 관리자 수동 처리 모두 동일 `payment_cancels` 행을 `PENDING`으로 되돌려 재사용한다. |
| 환불 실패 티켓 관리 | `REFUND_FAILED` 상태가 일정 기간 지속되면 관리자가 수동 재시도 또는 강제 취소로 처리한다.<br>사유와 집행자를 감사 로그에 남긴다. |
| PG 복구 | 승인·취소 결과가 불명확하거나 내부 반영에 실패하면 복구 작업을 등록한다.<br>승인 불명확은 `CONFIRM_UNCERTAIN`, 취소 불명확은 `CANCEL_UNCERTAIN`으로 구분한다.<br>취소 복구 시 PG 상태가 `CANCELED` 이면 로컬 결제를 취소 처리하고, `DONE` 이면 취소 API를 다시 요청한다.<br>비종결 상태·통신 실패는 재시도하며 동일 결제의 중복 복구·중복 환불을 차단한다.<br>`payment_cancels`의 `PENDING` 잔류 행도 동일한 복구 대상이다. |
| 회원 탈퇴 | `tickets.status`가 `ISSUED`(환불 기한 내)·`REFUND_PENDING`·`REFUND_FAILED`인 티켓이 1건이라도 있으면 차단한다.<br>`ISSUED`이더라도 환불 기한이 종료된 티켓, `USED_ENTERED`, `USED_NO_SHOW`, `REFUNDED`는 탈퇴를 막지 않는다. |
| 상태 변경 | 상태 변경은 검증을 포함한 도메인 메서드로만 수행한다. 검증을 우회하는 setter성 메서드를 두지 않는다. |
| 감사 로그 | 금전(결제·환불), 권한(회원 상태·역할), 티켓 상태, 좌석 판매 차단, 예매 상태 전이를 변경하는 모든 관리자 행위는 작업자·사유·변경 전후 값·시각을 기록한다. 전 도메인 공통이며 A·D·E는 필수다. |
| 외부 정보 | 출처와 기준 시각을 표시하고 장애 시 캐시 또는 대체 응답을 제공한다.  |
| 교통 알림 | 대상 경기의 예매 사용자에게 발송하며 동일 정체 이벤트의 중복 알림을 차단한다.  |
| 비밀값 | 비밀값을 코드와 설정 파일에 저장하지 않고 GitHub Secrets 또는 환경 변수로 주입한다. |
| 시간 기준 | 서비스·DB·API의 시간 기준을 `Asia/Seoul`로 통일하고 DB는 `DATETIME(6)` 을 사용한다. |

## 5. 주요 상태 전이

| 도메인 | 상태 |
| --- | --- |
| 좌석(`game_seats`) | `AVAILABLE → HELD → SOLD`, 취소·만료·환불 완료 `→ AVAILABLE`, 운영 차단 `AVAILABLE ↔ BLOCKED` |
| 예약(`reservations`) | `HOLDING → CONFIRMED / CANCELED / EXPIRED`<br>`CONFIRMED → CANCELED` (경기 전체 취소 또는 관리자 취소) |
| 주문(`orders`) | `CREATED → PAID / CANCELED / EXPIRED`<br>`PAID → PARTIALLY_CANCELED / CANCELED` |
| 결제(`payments`) | `READY → APPROVED / FAILED`<br>`FAILED → READY` (결제 수단 오류로 주문이 `CREATED` 상태인 경우 재시도)<br>`APPROVED → PARTIALLY_CANCELED / CANCELED`<br>`PARTIALLY_CANCELED → CANCELED`<br>`canceled_amount`가 `amount`에 도달하는 시점에 `CANCELED`로 전이한다. |
| 결제 취소(`payment_cancels`) | `PENDING → DONE`(PG 취소 성공) / `PENDING → FAILED → PENDING`(재시도) |
| 티켓(`tickets`) | `ISSUED → REFUND_PENDING → REFUNDED`(환불 성공)<br>`ISSUED → REFUND_PENDING → REFUND_FAILED → REFUND_PENDING`(재시도)<br>`ISSUED → USED_ENTERED`(QR 검표) / `ISSUED → USED_NO_SHOW`(경기 종료 후 배치) |
| 대기열(`queue_entry_histories`) | `WAITING → ADMITTED / CANCELED`, `CANCELED → WAITING`(재진입) |
| 입장 토큰(`admission_tokens`) | `ACTIVE → USED / EXPIRED / REVOKED / BROWSING_EXPIRED`<br>(USED 전이는 티켓 발급 시점, REVOKED는 대기 취소·재연결 유예 만료,<br>BROWSING_EXPIRED는 Queue-Token 발급 후 3분 안에 최초 좌석 선점을 완료하지 못한 경우) |
- 3차에서 주문·결제에 `PARTIALLY_CANCELED`가 추가되고, 티켓 상태가 6종으로 세분화된다.
- `payment_cancels.status`와 `tickets.status`는 1:1로 대응한다. 두 값이 불일치하면 정합성 위반으로 간주하고 복구 대상이다.
    - `PENDING ↔ REFUND_PENDING`
    - `DONE ↔ REFUNDED`
    - `FAILED ↔ REFUND_FAILED`
