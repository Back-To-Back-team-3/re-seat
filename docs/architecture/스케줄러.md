# 스케줄러

## 1. HoldExpiryScheduler — 좌석 선점(HOLD) 만료 회수

| 항목 | 값 |
| --- | --- |
| 파일 | `reservation/service/HoldExpiryScheduler.java` |
| 실행 방식 | `fixedDelay = 10초`, `initialDelay = 30초` |
| 트랜잭션 경계 | 스케줄러 자신이 아니라 `HoldExpiryService.releaseExpired()`에 위임(프록시 self-invocation 문제 회피) |

**동작**: `reservations.status = HOLDING`이면서 `hold_expires_at`이 지난 행을 `EXPIRED`로, 연결된 `game_seats.status = HELD`를 `AVAILABLE`로 같은 트랜잭션 안에서 함께 전이시킨다.

**동시성 설계 포인트**:

- UPDATE 순서를 `reservations → game_seats`로 고정한다.
    - 주문 생성 트랜잭션이 예약 행을 먼저 비관적 락으로 잡은 뒤 좌석을 갱신하는 순서와 동일하게 맞춰서 데드락 가능성을 줄인다.
- 두 UPDATE가 한 트랜잭션이라, "예약만 EXPIRED로 바뀌고 좌석은 HELD로 남는" 부분 회수 상태가 발생하지 않는다.
- 0건 회수는 매 사이클 로그를 남기지 않고 DEBUG로 억제한다 — 10초마다 도는 스케줄러가 로그를 도배하지 않도록 하는 설계다.

**명세서와의 관계**:

- API 명세서 §5.1(좌석 선점)·§5.2(선점 남은 시간 조회)
    - HOLD TTL 만료(스케줄러)
    - 부록 A "TTL 만료" 행과 정합적
- 선점 TTL 10분은 §5.1 본문에 명시된 값과 일치한다.
- 드리프트 없음.

## 2. OrderExpiryScheduler — 결제 기한 만료 주문 처리

| 항목 | 값 |
| --- | --- |
| 파일 | `order/service/OrderExpiryScheduler.java` |
| 실행 방식 | `fixedDelay = 10초`, `initialDelay = 30초` |
| 트랜잭션 경계 | `OrderExpiryService.expireOrders()`에 위임 |

**동작**: `orders.status = CREATED`이면서 결제 제한 시각을 넘긴 주문을 `EXPIRED`로 바꾸고, 연결된 예약(`HOLDING → EXPIRED`)과 좌석(`HELD → AVAILABLE`)까지 3단계를 한 트랜잭션에서 순차 처리한다.

**동시성 설계 포인트**:

- UPDATE 순서를 `Order → Reservation → GameSeat`으로 고정한다.

**HoldExpiryScheduler와의 관계**: 두 스케줄러가 겹치는 시나리오

- 주문이 생성되면서 `hold_expires_at`이 연장된 예약을, HoldExpiryScheduler가 "만료됐다"고 잘못 판단해 먼저 회수해버릴 수 있다.
- HoldExpiryScheduler는 `WHERE status='HELD' AND hold_expires_at < now()` 조건부 원자적 UPDATE로 수행하고, 주문 생성은 예약 행을 비관적 락으로 잡은 뒤 연장한다(API 명세서 §6.1 "선점 연장" 참고).
- 즉 이 두 스케줄러는 독립적으로 도는 것처럼 보이지만 실제로는 같은 행을 두고 경합하는 관계이므로, 둘 중 하나를 수정할 때는 반드시 다른 하나와의 경합 시나리오를 함께 검토해야 한다.

**명세서와의 관계 — 드리프트 있음**:

- 기존에 이 문서는 "API 명세서 §6.3(주문 취소)과 정합적"이라고 적혀 있었으나, §6.3은 사용자가 직접 `POST /orders/{orderId}/cancel`을 호출하는 **CREATED→CANCELED** 흐름이고, 이 스케줄러는 결제 시도 없이 기한이 지나 자동으로 넘어가는 **CREATED→EXPIRED** 흐름이라 서로 다른 API다.
- API 명세서 부록 A(좌석/예약 상태 전이)에는 이 스케줄러가 만드는 `orders: CREATED→EXPIRED` 전이에 대응하는 행이 없다. "TTL 만료"·"결제 실패 Case2" 행과는 트리거 조건이 다르므로 별도 행이 필요하다.
- **후속 조치**: API 명세서 부록 A에 아래 행 추가를 제안한다.
    
    
    | 단계 | `game_seats.status` | `reservations.status` | `orders.status` | 트리거 API |
    | --- | --- | --- | --- | --- |
    | 결제 기한 만료(미결제) | HELD→AVAILABLE | HOLDING→EXPIRED | CREATED→EXPIRED | (스케줄러) |

## 3. QueueAdmissionScheduler — 대기열 자동 입장 처리

| 항목 | 값 |
| --- | --- |
| 파일 | `queue/service/QueueAdmissionScheduler.java` |
| 실행 방식 | `fixedDelay = 3초`, `initialDelay = 3초` (`QueueAdmissionPolicy.ADMISSION_INTERVAL_MILLIS`) |
| 한 회차 처리량 | 경기당 최대 20명 (`QueueAdmissionPolicy.ADMIT_LIMIT`) |

**동작**: Redis에서 `queue:game:*` 패턴의 키를 `SCAN`으로 조회(`KEYS` 대신 사용 — Redis 서버 블로킹 방지)한 뒤, 경기별로 `AdmissionTokenService.admit()`을 호출해 대기 순서가 앞선 사용자부터 입장 토큰을 발급한다.

**설계 포인트**:

- 경기 하나의 입장 처리 실패가 다른 경기 대기열 처리 전체를 막지 않도록, 경기 단위로 예외를 개별 처리(`try-catch`)하고 로그만 남긴 뒤 다음 경기로 넘어간다.
- 인터럽트(스레드 종료 시그널)만은 예외적으로 다시 던져서 스케줄 실행 자체를 즉시 종료한다.
- 예상 대기시간 계산 공식: `(순번-1) / 20 + 1` 라운드 × 3초.

**명세서와의 관계 — 반영 완료(기존 "업데이트 필요" 해소)**:

- API 명세서 §3(대기열) 동작 흐름 7번 "자동 입장 스케줄러가 경기별 대기열 앞쪽 사용자를 주기적으로 처리한다"와 일치한다.
- 주기(3초)·배치 크기(20명)는 이제 API 명세서 §3.2에 `ceil(현재 순번 / 20) × 3초`로 이미 반영되어 있다(이 문서의 `(순번-1)/20+1` 공식과 수학적으로 동일하다). 이전 버전에서 "명세서에 수치 업데이트 필요"라고 남겼던 항목은 해소됐다.
- 드리프트 없음.

## 4. PaymentRecoveryScheduler — 결제 승인 상태 불명확 건 자동 복구

| 항목 | 값 |
| --- | --- |
| 파일 | `payment/schedule/PaymentRecoveryScheduler.java` + `PaymentRecoveryService.java` |
| 실행 방식 | `fixedDelay = 30초`, `initialDelay = 30초` |
| 배치 크기 | 20건(`RECOVERY_BATCH_SIZE`) |
| 재시도 정책 | 최대 5회, 재시도 간격 1분(`MAX_RETRY_COUNT`, `RETRY_DELAY_MINUTES`) |
| 대상 테이블 | `payment_recovery_tasks`(ERD 3.15) |

**동작**: 결제 승인 요청 처리 중 실패했지만, PG(Toss)에는 이미 승인이 찍혔을 수 있는 케이스(`type = CONFIRM_UNKNOWN`)를 `PaymentRecoveryTask` 엔티티(`PENDING`/`PROCESSING`/`RETRY`/`COMPLETED`/`FAILED`)로 큐잉해두고, 이 스케줄러가 주기적으로 꺼내 처리한다.

1. `PENDING` 또는 (`RETRY`이면서 `nextRetryAt`이 지난) 작업을 최대 20건 조회한다.
2. Toss에 실제 승인 상태를 재조회한다.
3. Toss에서는 승인됨 → 전액 취소(cancel) 호출 → 취소 완료 확인되면 `COMPLETED`.
4. Toss도 승인 실패/만료/취소 상태 → 그대로 `COMPLETED`(우리 쪽과 정합적이므로 복구 불필요).
5. 그 외 애매한 상태 또는 예외 발생 → 재시도 카운트 확인 후 `RETRY`(1분 뒤) 또는 5회 초과 시 `FAILED`.

**용어 정리 필요** — 명세서 7.7절과 비슷

| 구분 | 명세서 7.7 "PENDING 잔류 행 복구" | 코드 `PaymentRecoveryScheduler` |
| --- | --- | --- |
| 대상 테이블 | `payment_cancels` (아직 코드에 없음) | `payment_recovery_tasks` (실제 구현됨) |
| 트리거 조건 | 취소 요청(`payment_cancels.status=PENDING`)이 임계 시간 이상 잔류 | 결제 승인 요청 처리 중 실패해서 상태가 불명확해진 경우 |
| 목적 | "취소했는데 서버가 중간에 죽어서 취소 확정이 안 된" 케이스 복구 | "승인 요청했는데 서버가 중간에 죽어서 승인 여부를 모르는" 케이스 복구 |
| 구현 여부 | 미구현 (`payment_cancels` ) | 구현 완료 |
- **환불(취소) 쪽 복구 vs 승인 쪽 복구**

**설계 포인트**:

- 작업을 꺼낼 때 `findByIdWithPessimisticWriteLock`으로 비관적 락을 걸어, 같은 작업을 여러 스케줄러 인스턴스가 동시에 집으면 안 되는 경우(다중 인스턴스 배포 시)를 대비한다.
- Toss가 "이미 취소된 거래"로 응답하는 것과 "취소 확인 불가"를 구분해서, 전자는 성공으로 간주하고 후자만 재시도한다.

**명세서와의 관계**:

- API 명세서 §7.2 처리 규칙 9~10번(승인 상태 불명확 시 복구 작업 등록)과 정합적이다.
- ERD 3.15(`payment_recovery_tasks`)와 정합적. `type = CONFIRM_UNKNOWN`, `payment_cancel_id`는 `NULL`인 행이 이 흐름의 대상이다.

## 4-1. PartialCancelRecoveryHandler — 티켓 부분 취소(환불) 복구

| 항목 | 값 |
| --- | --- |
| 대상 테이블 | `payment_recovery_tasks`(`type = PARTIAL_CANCEL`, `payment_cancel_id` NOT NULL) + `payment_cancels` |
| 트리거 | 사용자 티켓 취소(§8.3), 재시도(§8.4), 관리자 강제 취소(§9.13, §9.19) — TTL 기반이 아니라 **환불 요청 접수 이벤트 기반** |
| 폴링 인프라 | 4번 `PaymentRecoveryScheduler`와 동일한 `payment_recovery_tasks` 폴링 루프를 공유하고, `type`으로 분기해 이 핸들러에 위임하는 구조로 추정된다(코드 레벨 클래스 분리 여부는 §9의 서비스 계층에서 재확인 필요). |

**동작**(API 명세서 §7.5 처리 규칙 기준):

1. Ticket 도메인이 환불 요청을 시작하고 티켓을 `REFUND_PENDING`으로 전이한다.
2. Payment 도메인이 티켓과 연결된 결제를 찾아 `payment_cancels`를 `PENDING`으로 선기록한다(PG 호출 전에 먼저 남겨 중복 환불을 차단).
3. 이 핸들러가 작업을 획득해 Toss 부분 취소 API를 호출한다.
4. Toss 취소 완료가 확인되면 `payment_cancels`를 `DONE`으로, Toss가 "이미 취소된 거래"로 응답해도 성공(`DONE`)으로 간주한다(4번 스케줄러와 동일한 원칙, 적용 대상만 승인이 아니라 취소).
5. 일부 금액만 취소되면 `payments`는 `PARTIALLY_CANCELED`, 전체 금액이 취소되면 `CANCELED`가 된다(취소 완료 금액은 컬럼으로 저장하지 않고 `payment_cancels` DONE 합계로 조회 시점에 산정 — ERD 6.4).
6. 성공 시 `ticketService.completeTicketRefund(ticketId)`를 호출한 뒤, 같은 흐름에서 `orderService.refundOrder(orderItemId)`를 호출해 `orders`와 `game_seats`를 정리한다.
7. 재시도 한도를 모두 소진하면 `TicketService.failTicketRefund(ticketId)`를 호출해 티켓을 `REFUND_FAILED`로 남긴다.
8. 동일 티켓의 기존 `FAILED` 취소 이력이 재시도되면 새 `payment_cancels` 행을 만들지 않고 기존 행을 `PENDING`으로 되돌려 재사용한다(`uk_payment_cancels_ticket`로 스키마 레벨 강제).

**4번(PaymentRecoveryScheduler)과의 관계**:

- 두 흐름은 서로 다른 문제를 복구하지만 같은 `payment_recovery_tasks` 테이블과 `recovery_key` 유니크 제약을 공유한다(ERD 3.15).

| 구분 | 4. 승인 불명확 복구 | 4-1. 부분 취소 복구 |
| --- | --- | --- |
| `type` | `CONFIRM_UNKNOWN` | `PARTIAL_CANCEL` |
| 트리거 조건 | 결제 승인 요청 처리 중 실패해서 상태가 불명확해진 경우 | 티켓 환불 요청이 접수된 경우(`payment_cancels` PENDING 선기록) |
| 목적 | "승인 요청했는데 서버가 중간에 죽어서 승인 여부를 모르는" 케이스 복구 | "PG 취소 요청했는데 서버가 중간에 죽어서 취소 확정이 안 된" 케이스 복구 |
| 트리거 방식 | TTL 기반 폴링(30초 주기, 전체 스캔) | 환불 요청 이벤트로 즉시 등록 + 동일 폴링 루프에서 재시도 |
| `payment_cancel_id` | NULL | NOT NULL |
| 구현 여부 | 구현 완료 | 구현 완료 |

## 종합: 스케줄러 간 상호작용

```
QueueAdmissionScheduler (3초)
  └─ 대기열 → 입장 토큰 발급
        │
        ▼
HoldExpiryScheduler (10초)  ⇄ 경쟁 ⇄  주문 생성 트랜잭션
  └─ 선점(HOLD) 만료 회수         (hold_expires_at 연장)
        │
        ▼
OrderExpiryScheduler (10초)
  └─ 결제 미완료 주문 만료 (Order→Reservation→GameSeat 순, CREATED→EXPIRED)

──────────────────────────────────────────────
(위 3개와는 독립된 트리거 — TTL이 아니라 이벤트 기반)

PaymentRecoveryScheduler (30초 폴링)
  ├─ type=CONFIRM_UNKNOWN → 승인 상태 불명확 결제 자동 복구 (PG 재조회 기반)
  └─ type=PARTIAL_CANCEL  → PartialCancelRecoveryHandler
                              └─ 티켓 부분 환불 확정/실패 처리 (payment_cancels 기반)
```

- HoldExpiryScheduler(10초)와 OrderExpiryScheduler(10초)가 같은 주기로 돌면서 서로 다른 트리거 조건(`reservations` vs `orders` 기준)으로 겹치는 좌석 행을 갱신할 수 있는 구조다.
- 두 스케줄러의 실행 순서가 매 사이클 보장되지 않는다. 둘 다 독립된 `@Scheduled`다.
- PaymentRecoveryScheduler 계열은 앞의 세 스케줄러와 달리 좌석 TTL과 직접 연결되지 않고, 결제·환불 이벤트에 의해 간접적으로 트리거된다는 점에서 성격이 다르다. 이번 개정에서 다이어그램을 "TTL 기반 파이프라인"과 "이벤트 기반 복구"로 분리해 표현했다.

### Q: 왜 HoldExpiryScheduler와 OrderExpiryScheduler를 통합하지 않았는가

- 책임 분리.
- 통합 시 트랜잭션 비대화 트레이드오프.

### Q: 왜 승인 복구와 부분 취소 복구를 같은 테이블(`payment_recovery_tasks`)로 통합했는가

- 둘 다 "PG 상태 기준으로 로컬 상태를 재조회·복구한다"는 동일한 처리 골격(비관적 락 획득 → PG 재조회 → 상태 확정/재시도/최종 실패)을 공유한다.
- 유니크 전략은 `payment_id` 단일 → `(payment_id, type)` → `recovery_key`로 두 번 재설계됐다(ERD 3.15 각주 참고). 같은 결제에 승인 복구 1건과 부분 취소 복구 여러 건(티켓별)이 동시에 존재할 수 있기 때문이다.
