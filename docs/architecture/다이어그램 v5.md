### 본인인증 및 예매 권한 획득 흐름

- `GET /api/v1/users/me` (실제 컨트롤러 `UserController`)
- `POST /api/v1/users/verification` (실제 `VerificationController`)
- 실제 흐름
    - 클라이언트가 `impUid`만 보내고, 서버가 PortOne에서 CI·실명·전화번호를 직접 조회한다.

```mermaid
sequenceDiagram
    autonumber
    actor Client as 클라이언트 (React)
    participant AuthFilter as Spring Security (JWT 필터)
    participant UserCtrl as UserController (api/v1/users)
    participant UserSvc as UserService (더티체킹)
    participant UserRepo as UserRepository (RDBMS)
    participant VerifCtrl as VerificationController (api/v1/users/verification)
    participant VerifSvc as VerificationService
    participant PortOne as PortOne API (외부)

    Client->>AuthFilter: [GET] /api/v1/users/me (Bearer JWT 토큰 탑재)
    activate AuthFilter
    Note over AuthFilter: 토큰 변조/만료 검증 및<br/>UserPrincipal 인증 객체 적재
    AuthFilter->>UserCtrl: 요청 위임 (@AuthenticationPrincipal 주입)
    deactivate AuthFilter

    activate UserCtrl
    UserCtrl->>UserSvc: getMyProfile(userId)
    activate UserSvc
    UserSvc->>UserRepo: findById(userId)
    UserRepo-->>UserSvc: User 객체 반환
    UserSvc-->>UserCtrl: UserProfileResponse (isVerified=false 반환)
    deactivate UserSvc
    UserCtrl-->>Client: ApiResponse.success("내 정보 조회 완료")
    deactivate UserCtrl

    Note over Client, UserCtrl: [PortOne 외부 SDK 실행 및 imp_uid 획득 완료 후]

    Client->>VerifCtrl: [POST] /api/v1/users/verification (imp_uid만 송신)
    activate VerifCtrl
    VerifCtrl->>VerifSvc: verifyAndUpdateUser(userId, impUid)
    activate VerifSvc
    VerifSvc->>PortOne: fetchVerificationInfo(impUid)
    PortOne-->>VerifSvc: 본인인증 결과 (CI, 실명, 전화번호) — 서버가 직접 조회
    Note over VerifSvc: 1. 이미 인증됐는지 검증<br/>2. 동일 CI 중복 가입 여부 검증<br/>3. name/phone/ci 갱신, isVerified = true 전환
    VerifSvc->>UserRepo: user.completeVerification(ci, name, phone)

    Note over VerifSvc: @Transactional 종료 시점에<br/>영속성 컨텍스트 '더티 체킹' 발생
    VerifSvc-->>VerifCtrl: 처리 성공
    deactivate VerifSvc
    VerifCtrl-->>Client: ApiResponse.success("본인인증 완료")
    deactivate VerifCtrl
```

### 비밀번호 변경 및 해시 검증 흐름

```mermaid
sequenceDiagram
    autonumber
    actor Client as 클라이언트 (React)
    participant UserCtrl as UserController (PATCH /users/me/password)
    participant UserSvc as UserService (비즈니스 로직)
    participant PwdEnc as PasswordEncoder (BCrypt)
    participant UserEnt as User 엔티티 (Domain)

    Client->>UserCtrl: PasswordChangeRequest (현재 비번, 새 비번 보냄)
    activate UserCtrl
    UserCtrl->>UserSvc: changePassword(userId, request)
    activate UserSvc

    Note over UserSvc: UserRepository를 통해<br/>현재 암호화된 유저 정보 획득

    UserSvc->>PwdEnc: matches(입력된 현재 비번, DB 내부 암호화 해시값)
    activate PwdEnc

    alt 비밀번호 불일치 시
        PwdEnc-->>UserSvc: false
        Note over UserSvc: InvalidPasswordException 터뜨림
        UserSvc-->>UserCtrl: Exception 전파 (GlobalExceptionHandler 수용)
        UserCtrl-->>Client: 400 Bad Request (비밀번호 오류 메시지)
    else 비밀번호 정확히 일치 시
        PwdEnc-->>UserSvc: true
        deactivate PwdEnc

        UserSvc->>PwdEnc: encode(새로운 비밀번호)
        PwdEnc-->>UserSvc: 새로운 암호화 해시 텍스트 반환

        UserSvc->>UserEnt: changePassword(newEncodedPassword)
        Note over UserEnt: 영속 상태의 패스워드 필드 스위칭
        UserSvc-->>UserCtrl: 완료 응답 반환
        deactivate UserSvc
        UserCtrl-->>Client: 200 OK (ApiResponse.success("비밀번호 변경 완료"))
    end
    deactivate UserCtrl
```

### 본인인증 예매 가드 레이어

- JWT → Queue-Token → 본인인증 → 수량 검증 순서와 에러코드(`MAX_SEAT_COUNT_EXCEEDED`)

```mermaid

    Start([사용자가 예매하기 클릭]) --> Step1{1단계: JWT 토큰 유효성 검증}
    Step1 -- 미인증 (401) --> Err1[401 Unauthorized / 로그인 유도]
    Step1 -- 통과 --> Step2{2단계: Queue-Token 보유 검증}
    Step2 -- 토큰 없음/조작 --> Err2[400 Bad Request / 대기실 강제 퇴장]
    Step2 -- 통과 --> Step3{3단계: 본인인증 검증 <br> users.is_verified == true}

    Step4 -- 초과 --> Err4[400 Bad Request / MAX_SEAT_COUNT_EXCEEDED]
```

- 클라이언트가 부르는 본인인증 API 경로: `POST /api/v1/users/verification`

```mermaid
sequenceDiagram
    autonumber
    actor User as 사용자 (React)
    participant Auth as Security (OAuth2)
    participant UserRepo as UserRepository
    participant PortOne as PortOne API
    participant VerifSvc as VerificationService

    %% 1단계: 소셜 로그인
    User->>Auth: 카카오 / 네이버 로그인 버튼 클릭
    Auth->>Auth: 소셜 로그인 및 사용자 프로필 획득

    alt 최초 로그인 사용자 (신규 가입)

    %% 2단계: 본인인증 게이트웨이

    Note over VerifSvc: 1. 기존 DB 내 동일 CI 중복 가입 체크<br/>2. 로그인한 유저 정보 획득

    VerifSvc->>UserRepo: 유저 엔티티 업데이트 (is_verified = true, name = 실명, phone = 전화번호)
    VerifSvc-->>User: 200 OK (본인인증 완료 및 예매 권한 활성화)

```

### 결제 승인 성공 및 티켓 발급 시퀀스

- 경로: `POST /api/v1/payments/{paymentId}/complete`

```mermaid
sequenceDiagram
    autonumber
    actor Client as 클라이언트 (React)
    participant PayCtrl as PaymentController
    participant PaySvc as PaymentService
    participant Toss as Toss Payments API (외부)
    participant OrderSvc as OrderService
    participant ReservSvc as ReservationService
    participant TicketSvc as TicketService
    participant QueueSvc as AdmissionTokenService (Queue 도메인)

    Client->>PayCtrl: [POST] /api/v1/payments/{paymentId}/complete<br/>(paymentKey, orderId, amount + Idempotency-Key 헤더)
    activate PayCtrl
    PayCtrl->>PaySvc: approvePayment(paymentId, request, idempotencyKey)
    activate PaySvc

    Note over PaySvc: 1. 결제 멱등성 검증 및 중복 승인 방지<br/>(READY 상태 확인)

    PaySvc->>Toss: [POST] Toss 승인 API 호출 (외부 I/O)
    activate Toss
    Toss-->>PaySvc: 승인 성공 응답 (200 OK)
    deactivate Toss

    rect rgb(240, 248, 255)
        Note over PaySvc, QueueSvc: [데이터베이스 정합성 및 상태 전이 연쇄]
        PaySvc->>PaySvc: 결제 상태 변경 (READY -> APPROVED)

        PaySvc->>OrderSvc: markPaid(orderId)
        Note over OrderSvc: 주문 상태 변경 (CREATED -> PAID)

        PaySvc->>ReservSvc: confirmReservation(reservationId)
        Note over ReservSvc: 1. 예약 상태 확정 (HOLDING -> CONFIRMED)<br/>2. game_seats 상태 전이 (HELD -> SOLD)

        PaySvc->>TicketSvc: issueTickets(orderId)
        Note over TicketSvc: order_items 개수만큼 Ticket 엔티티 생성<br/>(상태: ISSUED, 신규 qr_token 발급)

        PaySvc->>QueueSvc: consumeQueueToken(queueToken)
        Note over QueueSvc: admission_tokens 상태 전이 (ACTIVE -> USED)<br/>좌석 선점 시점에는 검증만 하고 소비하지 않았던 토큰을<br/>이 시점에 비로소 소비한다 (정책 및 상태 3.2절)
    end

    PaySvc-->>PayCtrl: 결제 완료 및 티켓 정보 반환
    deactivate PaySvc
    PayCtrl-->>Client: ApiResponse.success("결제 완료", PaymentCompleteResponse)
    deactivate PayCtrl
```

### 결제 실패 및 좌석 즉시 복구 시퀀스

- 결제 실패 처리시에는 토스 결제 API를 호출하지 않으며(결제 실패 API가 존재하지 않음), 내부적으로만 처리된다.
- 위젯 오류·재시도 가능한 실패는 클라이언트(Toss 위젯)가 자체적으로 처리하고, 서버의 `fail` API는 재시도 불가능한 종결 상황에서만, Toss를 호출하지 않고 내부 상태만 바꾼다.

```mermaid
sequenceDiagram
    autonumber
    actor Client as 클라이언트 (React)
    participant PayCtrl as PaymentController
    participant PaySvc as PaymentService
    participant OrderSvc as OrderService
    participant ReservSvc as ReservationService
    participant Redis as Redis Cache

    Note over Client: Toss 결제 위젯에서 사용자 취소·최종 실패 발생<br/>(재시도 가능한 오류는 위젯이 자체 처리하며 이 API를 부르지 않음)

    Client->>PayCtrl: [POST] /api/v1/payments/{paymentId}/fail (code, message, orderId)
    activate PayCtrl
    PayCtrl->>PaySvc: failPayment(paymentId, request)
    activate PaySvc

    Note over PaySvc: Toss API를 호출하지 않고<br/>내부 상태만으로 종결 처리 (재시도 불가 확정)

    rect rgb(255, 240, 240)
        Note over PaySvc, Redis: [안전한 자원 반환 및 롤백 프로세스]
        PaySvc->>PaySvc: 결제 상태 변경 (READY -> FAILED)

        PaySvc->>OrderSvc: cancelOrder(orderId)
        Note over OrderSvc: 주문 상태 변경 (CREATED -> CANCELED)

        PaySvc->>ReservSvc: releaseReservation(reservationId)
        Note over ReservSvc: 1. 예약 취소 전이 (HOLDING -> CANCELED)<br/>2. DB game_seats 원복 (HELD -> AVAILABLE)

        PaySvc->>Redis: deleteSeatHold(gameSeatId)
        Note over Redis: Redis 임시 선점 키(TTL) 즉시 삭제 처리
    end

    PaySvc-->>PayCtrl: 실패 처리 완료
    deactivate PaySvc
    PayCtrl-->>Client: ApiResponse.success("결제 실패 처리 완료")
    deactivate PayCtrl
    Note over Client: 사용자 화면을 좌석 선택 페이지로 안전 복귀시킴
```

### 도메인 전체 아키텍처 및 상태 흐름도

- 티켓은 `ISSUED` 이후 `REFUND_PENDING`/`REFUND_FAILED`/`REFUNDED`/`USED_ENTERED`/`USED_NO_SHOW`로 세분화된다. 이 세분화는 "예정"이 아니라 3차에서 이미 적용 완료됐다(T3-06, ERD 3.16).

```mermaid
stateDiagram-v2
    [*] --> Queue : 1. 예매하기 클릭

    state Queue {
        [*] --> Redis_ZSet : 진입순서(score) 등록
        Redis_ZSet --> SSE_Push : 실시간 대기 순번 전달
        SSE_Push --> Admission : 가용 트래픽만큼 통과
        Admission --> Queue_Token_Issued : 입장 토큰 발급
    }

    Queue --> Seat_Selection : 2. 입장 토큰 검증 완료 후 진입

    state Seat_Selection {
        [*] --> AVAILABLE : 좌석 탐색
        AVAILABLE --> HELD : 3. 좌석 임시 선점 (Redisson 분산 락)<br>※ HOLD_TTL 작동
    }

    Seat_Selection --> Reservation_Order : 4. 임시 선점 성공 (HOLDING)

    state Reservation_Order {
        [*] --> CREATED : 5. 주문 생성 및 결제 대기<br>※ PAYMENT_DEADLINE 작동
    }

    state Payment_Process {
        CREATED --> APPROVED : 6-A. 결제 성공 (idempotency-key 검증)
        CREATED --> FAILED_or_TIMEOUT : 6-B. 결제 실패 또는 타이머 종료
    }

    state Post_Purchase {
        APPROVED --> SOLD : 7. 좌석 확정 (RDBMS)
        SOLD --> ISSUED : 8. 1인당 최대 2매 이내 티켓 발급 (qr_token 부여)<br>※ 이 시점에 Queue-Token 소비 (ACTIVE -> USED)

        ISSUED --> REFUND_PENDING : 9-A. 사용자·관리자 취소 요청 접수<br>(payment_cancels PENDING 선기록)
        REFUND_PENDING --> REFUNDED : 9-B. PG 부분/전체 취소 확정<br>(game_seats: SOLD -> AVAILABLE)
        REFUND_PENDING --> REFUND_FAILED : 9-C. PG 취소 실패<br>(game_seats는 SOLD 유지)
        REFUND_FAILED --> REFUND_PENDING : 9-D. 재시도(사용자/관리자)

        ISSUED --> USED_ENTERED : 10-A. QR 검표 성공
        ISSUED --> USED_NO_SHOW : 10-B. 미입장 상태로 경기 종료(배치)
    }

    FAILED_or_TIMEOUT --> AVAILABLE : 11. 보상 트랜잭션 (HELD 해제, 예약/주문 CANCELED 또는 EXPIRED)
```

### 일반 사용자 상세 시퀀스

- 대기열 → 가드 → 선점 → 주문/결제
- `HOLD_TTL 10분`

```mermaid
sequenceDiagram
    autonumber
    actor User as 사용자 (React)
    participant Queue as QueueService (Redis ZSet)
    participant Auth as Security (is_verified 검증)
    participant Seat as SeatInventoryService (Redisson)
    participant Order as Order/PaymentService
    participant Toss as Toss PG API
    participant Ticket as TicketService

    %% 1. 대기열 단계
    User->>Queue: KBO 경기 예매 요청
    activate Queue
    Queue->>Queue: Redis ZSet에 사용자 진입 순서 적재
    loop 매 초 반복
        Queue-->>User: SSE 실시간 순번 & 예상 대기 시간 푸시
    end
    Queue->>Queue: 동적 admission (초당 N명 진입 허용)
    Queue-->>User: Queue-Token 발급 (입장 승인)
    deactivate Queue

    %% 2. 예매 진입 및 가드 레이어 검증
    User->>Auth: 좌석 선택 화면 진입 시도 (Queue-Token + JWT 제출)
    activate Auth
    Note over Auth: 1. 본인인증(is_verified == true) 여부 검증<br/>2. 1인당 최대 수량(2매) 제한 검증
    Auth-->>User: 검증 통과 (진입 허용)
    deactivate Auth

    %% 3. 좌석 선점 (HOLD) 단계
    User->>Seat: 좌석 선택 및 선점 요청 (Seat ID)
    activate Seat
    Note over Seat: Redisson 분산 락 획득 시도
    alt 다른 사용자가 먼저 선점한 경우
        Seat-->>User: 400 Bad Request (이미 선택된 좌석입니다.)
    else 선점 성공 시
        Seat->>Seat: 1. game_seats 상태 전이 (AVAILABLE -> HELD)<br/>2. Redis HOLD_TTL (10분) 타이머 시작
        Seat-->>User: 좌석 선점 완료 (주문 작성 페이지 이동)
    end
    deactivate Seat

    %% 4. 주문 및 결제 단계
    User->>Order: 주문서 작성 및 결제 요청 (idempotency-key 포함)
    activate Order
    Note over Order: 주문 생성 (CREATED)<br/>PAYMENT_DEADLINE 타이머 설정 (HOLD_TTL 이하)
    Order->>Toss: 결제 승인 요청 (paymentKey, amount)
    Toss-->>Order: 결제 성공 응답 (APPROVED)

    rect rgb(240, 248, 255)
        Note over Order, Ticket: [트랜잭션 확정 체인]
        Order->>Order: 주문 상태 업데이트 (CREATED -> PAID)
        Order->>Seat: 좌석 상태 최종 전이 (HELD -> SOLD)
        Order->>Ticket: 티켓 일괄 발급 (order_item당 1장, ISSUED)
    end

    Order-->>User: 예매 최종 완료 (모바일 티켓 및 QR 활성화)
    deactivate Order
```

### 티켓 부분 환불(취소) 시퀀스

- 경로: `POST /api/v1/tickets/{ticketId}/cancel` (§8.3), 재시도 `POST /api/v1/tickets/{ticketId}/cancel/retry` (§8.4)
- 접수(동기)와 확정(비동기)이 분리되어 있다. 클라이언트는 접수 응답만 받고, 최종 결과는 티켓/결제 조회로 재확인한다.
- 취소 이력을 PG 호출 **전에** `PENDING`으로 먼저 남기는 이유: PG 취소가 성공한 직후 서버가 죽으면 자금은 나갔는데 내부 상태는 그대로 남는 문제를 막기 위해서다(ERD 6.4 설계 판단).

```mermaid

    actor Client as 클라이언트 (React)

    participant TicketSvc as TicketService

    Note over TicketSvc: tickets.status: ISSUED -> REFUND_PENDING

    Recovery->>Toss: 부분 취소(cancel) API 호출

    alt Toss 취소 성공 (또는 "이미 취소된 거래" 응답)
        Toss-->>Recovery: 취소 완료 응답
        Recovery->>Recovery: payment_cancels.status: PENDING -> DONE
        Recovery->>PaySvc: 결제 금액 재계산
        Note over PaySvc: 취소 완료 금액 산정(payment_cancels DONE 합계)<br/>0 < 취소액 < amount → PARTIALLY_CANCELED<br/>취소액 = amount → CANCELED

        Note over TicketSvc: tickets.status: REFUND_PENDING -> REFUNDED
        Recovery->>OrderSvc: refundOrder(orderItemId)
        OrderSvc->>Seat: gameSeat.refund()
        Note over Seat: game_seats.status: SOLD -> AVAILABLE<br/>(REFUNDED 확정 이후에만 반환 — 순서 중요)
        OrderSvc->>OrderSvc: order.partiallyCancel() 또는 order.cancel()
    else Toss 취소 실패(네트워크/PG 오류)
        Toss-->>Recovery: 실패 응답 또는 타임아웃
```

- 관리자 강제 취소(§9.19 경기별 일괄 취소 포함)도 진입점만 `AdminTicketController`로 다를 뿐, `TicketService.cancelTicketByAdmin()` 이후는 위와 동일한 파이프라인을 그대로 탄다.
