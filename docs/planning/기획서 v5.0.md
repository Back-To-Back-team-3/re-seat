## 1. 프로젝트 개요

### 1.1 서비스 소개

**Re:Seat는 공정한 대기 → 안전한 좌석 선점 → 일관된 주문·결제 → QR 티켓으로 이어지는 KBO 경기 예매 플랫폼이다.**

인기 경기 예매에는 순간적인 트래픽 집중, 대기열 우회, 좌석 중복 선점과 중복 결제 위험이 함께 발생한다. Re:Seat는 대기열과 입장 토큰으로 요청을 제어하고, 좌석 HOLD와 동시성 제어로 재고 정합성을 보장하며, 주문·결제·티켓 상태를 하나의 예매 흐름으로 관리한다.

3차에서는 기존 흐름의 미완료 연동을 마무리하고 핵심 예매 흐름(대기열 → 좌석 선점 → 주문 → 결제 → 티켓)과 도메인별 관리자 기능, 외부 정보 연동(구장 혼잡도·지도)과 운영 모니터링을 고도화한다.

### 1.2 해결 과제

| 해결 과제 | 해결 방향 |
| --- | --- |
| 예매 시작 시 서버와 DB에 요청이 집중된다. | Redis ZSet과 Kafka로 요청을 완충하고 SSE로 순번과 입장 상태를 전달한다. |
| 대기열 진입 요청 자체에 트래픽이 몰리면 대기열 API가 먼저 과부하된다. | 순번 없는 1차 진입 게이트로 동시 진입 요청을 차단하고, 진입 요청은 Kafka 비동기 접수(202 Accepted)로 동기 처리 구간을 축소한다. |
| 동일 좌석에 요청이 몰리면 중복 선점이 발생할 수 있다. | 좌석 HOLD, TTL, DB 검증과 Redisson 분산 락을 함께 적용한다. |
| 대기열을 거치지 않은 직접 접근은 예매 공정성을 해친다. | Queue-Token을 예매 진입 조건으로 사용한다. |
| 재시도와 장애가 주문·결제·티켓 상태를 어긋나게 할 수 있다. | 멱등 처리, 상태 전이 검증과 PG 상태 기반 복구 절차를 적용한다. |
| 환불 중 PG 응답이 유실되면 자금과 내부 상태가 어긋난다. | 취소 이력을 PG 호출 전에 선기록하고, 티켓 상태를 환불 단계별로 분리한다. |
| 1인이 반복 요청으로 수량 제한을 우회할 수 있다. | 요청 단위가 아니라 누적 보유 기준으로 서버에서 검증한다. |
| 경기 정보와 운영 상태가 여러 서비스에 분산되어 있다. | 외부 정보를 통합하고 사용자 안내와 운영 대시보드를 제공한다. |

### 1.3 서비스 대상

- 예매 혼잡과 빠른 매진으로 원하는 좌석 예매에 어려움을 겪는 KBO 팬
- 대기 순번, 좌석 확보 여부와 남은 시간을 명확하게 확인하고 싶은 사용자
- 경기·좌석·예매 상태를 도메인별로 관리해야 하는 운영자

### 1.4 주요 이용 시나리오

| 시나리오 | 사용자 행동 | 기대 결과 |
| --- | --- | --- |
| 경기 정보 확인 | 홈에서 당일 경기 일정과 구장 위치·혼잡도를 확인한다.<br>예매페이지에서 전체 경기 일정을 확인한다. | 예매 전에 필요한 정보를 한 화면에서 파악한다. |
| 인기 경기 예매 | 경기 선택 후 대기열에 진입하고 순번에 따라 좌석 선택 화면으로 이동한다. | 대기열 우회 없이 공정한 순서로 예매한다. |
| 좌석 선택·결제 | 좌석 현황을 참고해 좌석을 선점하고 제한 시간 안에 결제한다. | 중복 선점 없이 주문·결제·티켓 상태가 일관되게 확정된다. |
| 예매 내역 관리 | 마이페이지에서 결제와 티켓을 확인하고 취소 가능한 티켓을 환불한다. | 선택한 티켓과 금액만 취소되고 나머지 예매는 유지된다. |
| 경기장 이동 | 지도에서 구장 위치와 혼잡도를 확인한다. | 경기장 이동 지연에 미리 대응한다. |
| 서비스 운영 | 관리자가 담당 도메인의 데이터와 상태를 조회·변경한다. | 권한 범위 안에서 예매 시스템을 운영하고 장애 상황에 대응한다. |

### 1.5 성공 기준

| 구분 | 기준 | 확인 방법 |
| --- | --- | --- |
| 전체 흐름 | 로그인부터 대기열, 좌석 선점, 주문, 결제와 티켓 확인까지 중단 없이 진행된다. | E2E 회귀 시나리오 |
| 좌석 정합성 | 동일 좌석 동시 요청의 성공은 1건이며 초과 예매는 0건이다. | 동시성 통합 테스트, k6 |
| 좌석 병렬성 | 서로 다른 좌석 요청이 전역 락으로 직렬화되지 않음 | k6, TPS 비교 |
| 대기열 공정성 | Queue-Token 검증을 통과하지 않은 좌석 접근은 차단된다. | 토큰 우회 테스트 |
| 결제 정합성 | 중복 승인 없이 실패·취소·환불·복구 결과가 관련 도메인에 일관되게 반영된다. | 멱등키 동시성 테스트 |
| 환불 정합성 | PG 취소 성공 후 DB 반영이 실패해도 재요청 시 이중 환불이 발생하지 않는다. | PENDING 잔류 행 복구 테스트 |
| 수량 제한 | 1좌석씩 반복 선점을 포함해 누적 2매 초과 0건  | 반복 선점 통합 테스트 |
| 화면 정합성 | 서버가 거절한 요청이 화면에 성공으로 보이지 않고, 사용자가 갇히는 경로가 없다. | 프론트 E2E 확인 |
| 운영 가시성 | 핵심 흐름의 지연, 오류율, 처리량과 자원 상태를 조회 수 있다. | Prometheus/Grafana 대시보드 |
| 락 전략 비교 | 비관적·낙관적·분산 락의 TPS·p99·실패율·초과예매를 동일 조건에서 비교한다. | k6 부하 측정 리포트 |

### 3.2 기본 예매 흐름

1. 사용자는 카카오 OAuth2 로그인으로 인증하고 JWT를 발급받는다.
2. PortOne 본인 인증을 완료해야 좌석 선점이 가능하다(미인증 시 403).
3. 경기 선택 후 대기열(Redis ZSet + Kafka 비동기 접수)에 진입한다.
4. SSE로 순번·입장 상태를 확인하고, 입장 시 Queue-Token을 발급받는다. 
    - 대기 인원이 없으면 즉시 admit 이벤트가 도착한다.
5. 좌석 현황을 조회하고 최대 2좌석을 선점한다. 
    - 선점 시점에는 Queue-Token을 검증만 하고 소비하지 않는다.
6. 다좌석 선점 시 `gameSeatId` 오름차순 정렬 후 Redisson 분산 락을 획득해 순환 대기를 차단하며, 락은 트랜잭션 경계 바깥에서 획득·해제한다.
7. 선점 좌석으로 주문을 생성하고 제한 시간 안에Toss Payments로 결제한다.
    - Queue-Token은 티켓 발급 시점에 소비한다.
8. 결제 성공 시 주문·예약·좌석을 확정(SOLD)하고 티켓을 발급한다.
9. 실패·취소·만료 시 관련 상태를 정책에 따라 복구한다.
    - 실패·취소·만료 시 좌석을 즉시 재선점 가능 상태로 되돌린다.
    - 일부 티켓만 선택한 부분 환불
        - 취소 이력을 PG 호출 전에 `PENDING`으로 선기록한 뒤 PG를 호출해 중복 환불을 차단한다.
        - 승인 응답 유실·내부 반영 실패는 PG 재조회 기반 복구 스케줄러가 처리한다.
10. 발급된 티켓은 마이페이지에서 티켓 기준으로 통합 조회하며, QR 검표로 입장을 확인한다.

## 5. 시스템 설계

### 5.1 구성

```
[React Client]
  ├─ 사용자: 홈 / 예매 / 마이페이지 
  └─ 관리자: 도메인별 관리 화면
          │ HTTP / SSE
          ▼
[Spring Boot]
  ├─ User / Verification
  ├─ Game / Stadium / SeatInventory / Reservation
  ├─ Queue(진입 게이트 + 대기열) / Order
  ├─ Payment / PaymentCancel
  ├─ Ticket
  ├─ CityData(서울시 실시간 도시데이터, 구장 혼잡도)
  └─ Admin((경기·좌석·예약·대기열·티켓 + 공통 감사 로그)
          │
          ├─ MySQL: 최종 상태와 이력 
          ├─ Redis·Redisson: 진입 게이트, 대기열, 임시 선점, 분산 락 
          ├─ Kafka: 대기열 진입 · 입장 이벤트 
          ├─ Toss Payments / OAuth2(카카오) / PortOne
          ├─ 서울시 실시간 도시데이터 API / 카카오맵 API
          └─ Prometheus / Grafana: 지표 수집 
```

### 5.2 설계 원칙

- Redis는 대기열·임시 상태·락을 담당하고 최종 상태는 MySQL에서 검증한다.
- 좌석은 결제 전까지 HOLD로 관리하고 결제 성공 후 SOLD로 확정한다.
- 락 획득과 해제는 트랜잭션 경계 바깥에서 수행한다. 트랜잭션 안에서 락을 해제하면 커밋 전에 락이 풀려 다른 요청이 아직 커밋되지 않은 상태를 읽고 초과 예매가 재발한다.
- 다좌석 선점 시 `gameSeatId` 오름차순으로 정렬한 뒤 락을 획득해 순환 대기를 구조적으로 차단한다.
- 서로 다른 좌석에 대한 요청은 병렬 처리되어야 한다. 전역 락으로 직렬화되면 설계 실패로 간주한다.
- 외부 결제와 API 호출은 DB 트랜잭션을 길게 점유하지 않도록 분리하고 실패 복구 기준을 둔다.
- 상태 변경은 도메인 메서드로 수행하며 다른 도메인의 Entity를 직접 수정하지 않는다.
- 도메인 간 호출은 구현 전에 계약을 확정한 뒤 병렬 개발한다.
- DTO와 Swagger를 API 계약의 기준으로 사용한다.
- 관리자 기능은 `admin` 패키지로 분리해 일반 사용자 플로우와 로직을 물리적으로 분리한다.

### 5.4 주요 설계 판단

| 판단 | 근거 | 감수한 단점 |
| --- | --- | --- |
| 가상 대기열로 예매 진입 제어 | 서버 증설만으로는 동일 시점의 좌석 요청 집중과 공정성 문제를 해결하기 어렵다. | 사용자는 즉시 진입하지 못하고 대기 시간이 발생한다. |
| Redis 임시 상태와 MySQL 최종 상태 분리 | 빠른 순번·HOLD·TTL 처리는 Redis가 담당하고 영속 정합성은 MySQL에서 보장한다. | 두 저장소 간 동기화 실패 지점이 생기므로 DB 재검증이 필요하다. |
| 물리 좌석과 경기별 재고 테이블 분리 | 가격과 상태는 좌석의 속성이 아니라 좌석과 경기 조합의 속성이다. | 경기 생성 시 재고 일괄 생성 비용이 발생한다. |
| 락을 트랜잭션 경계 바깥에 배치 | 트랜잭션 안에서 락을 해제하면 커밋 전 상태를 다른 요청이 읽어 초과 예매가 재발한다. | 락 보유 시간이 트랜잭션보다 길어져 처리량이 소폭 감소한다. |
| 예매 자격·수량을 서버에서 강제 | 요청 크기 제한만으로는 반복 요청 우회를 막을 수 없다. | 선점 경로에 집계 조회가 추가된다. |
| Queue-Token을 티켓 발급 시 소비 | 선점 시 소비하면 선점 실패·취소마다 토큰이 소모되어 대기열 재진입을 강요하게 된다. | 토큰이 동시 입장 슬롯을 최대 발급 유효시간만큼 점유해 슬롯 회수가 늦어진다. |
| Queue-Token과 CAPTCHA 연계(확장 범위) | 정상 대기 사용자의 입장 권한을 확인하고 자동화된 좌석 접근을 추가 차단한다. | 정상 사용자에게도 추가 단계가 발생한다. |
| 결제 결과 기반 최종 확정 | 결제 성공 전에는 좌석을 임시 선점으로 유지해 실패·이탈 시 다시 사용할 수 있게 한다. | 미결제 좌석이 최대 18분간 점유된다. |
| PG 상태 기반 복구 | 승인 응답 유실이나 내부 반영 실패 시 PG 최종 상태를 기준으로 도메인 상태를 복구한다. | 복구 작업 큐와 재시도 정책이라는 별도 컴포넌트가 필요하다. |
| 취소 이력을 PG 호출 전에 선기록 | PG 취소 성공 직후 서버가 중단되면 자금은 나갔는데 내부 상태는 승인으로 남는다. `payment_cancels`를 `PENDING`으로 먼저 남겨야 재요청 시 이 구간을 식별하고 PG 재조회로 복구할 수 있다. | 정상 흐름에도 DB 쓰기가 1회 추가되고, `PENDING` 잔류 행을 정리하는 스케줄러가 필요하다. |
| 티켓 상태를 환불 단계별로 분리 | `CANCELED` 단일 상태로는 "환불 중"과 "환불 실패"를 구분할 수 없어 좌석 반환 시점과 수량 회복 시점을 판단할 수 없다. | 상태가 6종으로 늘어 검표·조회·탈퇴 검증 등 티켓 상태를 읽는 모든 지점의 조건을 재검토해야 한다. |
| 취소·재선점 시 예약 단위 복합 UNIQUE로 재설계 | 전역 UNIQUE 제약이 취소된 좌석의 재선점을 막는 버그를 유발해, 예약 단위 복합 UNIQUE로 좁혀 동일 좌석의 반복 취소·재선점을 허용했다. | 동일 예약 내 좌석 중복 삽입 방지라는 원래 목적은 애플리케이션 레벨 검증과 병행해야 한다. |
| 외부 정보 서울시 실시간 도시데이터로 통합 | 혼잡도·기상 정보를 단일 API·Redis 캐시로 받아 지도 시각화와 함께 제공할 수 있어 연동 복잡도를 줄였다. | 기상청 대비 예보 정확도·갱신 주기 차이가 있을 수 있어 기준 시각 표기가 필요하다. |
| 관리자 감사 로그를 구조화 로그로 우선 대체 | 정식 이력 테이블 없이도 커밋 성공 시점(`afterCommit`)에만 기록해 롤백된 시도가 남지 않도록 했다. | 검색·집계가 로그 시스템에 의존하며, 별도 테이블 전환 전까지는 관리자 화면에서 이력을 조회할 수 없다. |

## 7. 검증 계획

기능별 완료 기준은 3차 구현 범위 표를 따른다. 다음 항목은 여러 도메인에 걸친 공통 검증 기준이다.

| 영역 | 검증 내용 | 목표 |
| --- | --- | --- |
| 검증 실행성 | 동시성·부하 관련 테스트가 CI에서 실제로 실행되는지 | 비활성화 테스트 0건 |
| E2E | 실제 로그인부터 티켓 확인, 실패·취소·만료 흐름 | 핵심 시나리오 전체 통과 |
| 예매 자격·수량 | 미인증 사용자 선점, 1좌석씩 반복 선점, 취소 후 재선점 | 미인증 접근 차단 100%, 누적 수량 초과 0건 |
| 좌석 정합성 | 시나리오 A(동일 좌석 병렬), 시나리오 B(서로 다른 좌석 병렬) | A: 성공 1건·초과 0건 / B: 직렬화되지 않음을 TPS로 확인 |
| 락 전략 비교 | 비관적·낙관적·분산 락을 동일 시드와 동일 시나리오로 측정 | 4개 지표 확보, 전략별 2회 이상 반복으로 환경 편차 확인 |
| 대기열(Queue-Token) | 중복 진입, 이탈·재진입, 토큰 우회 | 중복 참여·검증 우회 0건 |
| 1차 진입 게이트·CAPTCHA | 게이트 통과·거절, CAPTCHA 위조·재사용 | 게이트 적용 전후 p99·오류율 비교 |
| 결제·환불·복구 | 중복 승인, 부분 환불, 동일 티켓 중복 취소 요청, PG 성공 후 DB 실패 재요청, 4xx/5xx·타임아웃 | 중복 처리·이중 환불·최종 상태 불일치 0건 |
| 운영 | p99, 오류율, 처리량, 자원 사용량 | 동일 환경에서 기준선과 개선 결과 비교 |
| 외부 정보 | 지연·실패·데이터 누락 | 대체 응답(캐시) 제공 |
- 테스트는 기능 구현과 함께 작성하고, 수정한 버그의 재현 테스트를 회귀 테스트로 유지한다.
- 부하 테스트 결과에는 환경, 요청 수, 성공·실패 수, TPS, p99를 함께 기록한다.
- 측정 환경(인스턴스 사양, 커넥션 풀, 좌석 수, VU 수)을 고정하고 리포트에 명시한다.
